Executive Summary

SortView is further along than a typical portfolio project. There is a real ingestion pipeline (Windows agent → FastAPI → Postgres), a real multi-tenant schema (organizations, branches, plans, subscriptions, feature entitlements, memberships), a real auth system with lockouts and an audit log, and a real automated test suite for the core business logic. That's the hard, unglamorous 60% that most side projects skip.

What's missing is almost entirely productization, not engineering fundamentals: billing, a repeatable install story for a new library's AMH machine, security hardening for an internet-facing product, and the compliance paperwork that any library's IT director will ask for before signing anything. That's a favorable gap to have — it says the hard part is done and the remaining work is well-scoped.

Bottom line: not sellable to an external library today, but a focused 6–10 week push (detailed in the roadmap below) closes most of the gap between "works for one customer we hand-hold" and "a product a second library can install without you in the room."

02

What's Already Solid

Worth stating plainly, because it's the part an interviewer will actually probe on:

✓

A real multi-tenant schema — organizations, branches, memberships, subscriptions, plans, feature_entitlements — wired into working tenant_service, entitlement_service, and permission_service layers, not just a customer_id column bolted on.

✓

Password auth done properly: werkzeug hashing, failed-login lockouts, and a genuine auth_audit_log table recording every login/lockout/password-change event.

✓

The AMH agent tracks local state, uploads incrementally, and retries with backoff — it won't silently re-send or silently drop data on a flaky connection.

✓

Idempotent writes: uploads use ON CONFLICT DO NOTHING against real unique constraints, matching an at-least-once delivery design.

✓

Schema changes go through Alembic, not ad hoc SQL or startup-time table creation — and the docs explicitly forbid the shortcuts that cause the worst production incidents.

✓

CI runs the full pytest suite on every push and PR — small, but it's a real gate, not aspirational.

✓

docs/deployment.md and docs/release-process.md read like actual internal runbooks — validation checklists, rollback mindset, deployment ordering — well above typical portfolio documentation.

✓

Recent commit history shows real hardening in progress: composite tenant-scoped indexes, fixing a cache-wiping performance regression, correcting the baseline migration for a view and missing sync triggers. That's an iterating engineer, not a one-shot demo.

03

Gap Analysis

Grouped by domain. Severity reflects risk if you onboarded a second, unsupervised library customer tomorrow.

Security & Auth

GapWhy it mattersSeverity
No rate limiting on main.py endpoints Login, /upload, and agent-token auth have no throttling — only the login form has attempt-lockout. The API is otherwise open to brute force / abuse from any internet client. Critical
Hardcoded guest fallback credentials src/app.py defaults SORTVIEW_GUEST_EMAIL/SORTVIEW_GUEST_PASSWORD to guest@gmail.com/guest if the env vars aren't set. Fine for the public demo; dangerous if that fallback ever ships in a real tenant's environment by mistake. High
No self-service password reset change_password in auth_service.py requires knowing the current password — there's no "forgot password" recovery path. Every locked-out library staffer becomes a support ticket. High
No MFA, no SSO/OAuth Library IT departments routinely require SSO against their existing identity provider before approving a new vendor app. High
No dependency/SAST scanning No Dependabot config, no pip-audit/bandit step in CI — python-tests.yml only runs pytest. High
Errors go to stdout only main.py catches exceptions with print() + traceback.print_exc() — no structured logging, no error tracking (Sentry or similar), so a production incident produces no alert. High

Testing & Code Quality

GapWhy it mattersSeverity
Zero tests on the tenant-isolation layer 8 test files cover alerts, metrics, transit logic, parsers, auth, and the API — but tenant_service.py, entitlement_service.py, permission_service.py, and access_service.py have no tests at all. That's precisely the code that keeps Library A from seeing Library B's data. Critical
No lint or type-check gate in CI CI runs pytest only. No ruff/flake8/mypy step to catch the class of bug below before it merges. High
Found in review

src/services/tenant_service.py defines get_organization_by_slug, get_branch_by_slug, and get_effective_settings twice (lines ~114–281, then duplicated again at ~282–439). Python silently keeps the second definition, which means the second, shallow-merge get_effective_settings ({**org_settings, **branch_settings}) is the one that actually runs — the first version's _deep_merge_settings helper is dead code that never executes. Net effect: nested branch-level settings that override only part of a nested org-level setting will silently wipe the rest of that setting instead of merging into it. Worth a five-minute fix, and exactly the kind of bug a lint pass or a test on get_effective_settings would have caught immediately.

Deployment & Operations

GapWhy it mattersSeverity
Agent install is fully manual, per site docs/release-process.md describes copying files by hand onto the AMH-attached Windows machine and re-running the scheduled task. For "install this at another library," this is the single biggest blocker — it doesn't scale past sites you can personally visit or remote into. Critical
No containerization, no CD No Dockerfile anywhere in the repo. Backend and dashboard deploys are "push to GitHub, then manually deploy or restart" per the runbooks — functional, but manual and unrepeatable at any scale. High
Known Python version drift (dev/CI vs. prod) CI pins 3.11; Streamlit Cloud's runtime pinning is reportedly broken. Flagged previously and still open — dependency behavior isn't guaranteed to match between where it's tested and where it runs. High
No monitoring, alerting, or documented backup/restore test No uptime or pipeline-health alerting beyond the dashboard's own pipeline-status panel (which requires a human to be looking at it). No evidence of a tested Neon restore procedure. High

Commercial & Legal Readiness

GapWhy it mattersSeverity
Patron-linked data, no documented privacy posture acs_events.patron_id plus barcode/title fields in checkins mean this system touches circulation-adjacent, patron-linked records. Most U.S. states have library patron-confidentiality statutes governing exactly this kind of data. There is no documented retention policy, no stated encryption-at-rest posture, and no DPA template — all of which a library's legal/IT review will ask for before signing. Critical
No billing integration The schema already has a stripe_customer_id column on subscriptions and a real plans/feature_entitlements model — but nothing calls Stripe. There's no trial-to-paid flow, no invoicing, no self-serve checkout. High
Onboarding is an internal admin action super_admin/pages/Provision_Library.py provisions a new org/branch, but it's an internal tool, not a signup flow a prospective library could use themselves. High
No LICENSE, ToS, or SLA The README's disclaimer frames this as an independent portfolio project. Before pitching it as a product to an institution, the IP terms and support expectations need to be explicit. Medium

Roadmap

Four phases, roughly in dependency order. Phase 0 is cheap and should happen regardless of what comes next; Phase 2 is what actually turns this into something you can put in front of a second library.

0Fix now

Zero-cost corrections

~1–2 days

  • Fix the tenant_service.py duplicate-definition bug and restore the deep-merge behavior for branch settings.
  • Gate or remove the hardcoded guest-credential fallback outside the demo deployment.
  • Pin and verify the Python version end-to-end (local / CI / Streamlit Cloud) to close the known drift.
  • Add a LICENSE file and decide the IP terms before any external conversation.
1Harden

Safe for a second real customer

~2–4 weeks

  • Tests for tenant_service, entitlement_service, permission_service, access_service — the tenant-isolation layer.
  • Structured logging and error tracking in place of print()/traceback.
  • Rate limiting on login, /upload, and agent-token endpoints.
  • Self-service password reset flow.
  • CORS/security headers, plus pip-audit and a lint/type-check step added to CI.
  • A written, tested backup/restore runbook for Neon.
2Productize

Actually sellable as multi-tenant SaaS

~4–8 weeks

  • Wire up Stripe against the existing subscriptions/plans schema — trial, upgrade, invoicing.
  • Turn Provision_Library.py into a guided onboarding flow a prospective customer can drive.
  • Containerize the backend and dashboard; add an actual CD pipeline instead of manual deploys.
  • Build a packaged, versioned installer/updater for the Windows AMH agent — this replaces the manual copy-paste-per-site process and is the real unlock for "install this at another library."
  • SSO / OAuth against common identity providers.
  • A written data-handling policy for patron-linked fields, checked against library-confidentiality statutes, with a stated retention and encryption-at-rest posture.
3Scale

Polish, ongoing

ongoing

  • Monitoring, alerting, and an uptime SLA; load testing for peak sort-shift traffic.
  • MFA; be ready for a security questionnaire from a library consortium's IT office.
  • ToS/DPA templates, a pricing page, sales collateral.
  • Expand automated coverage to the Streamlit views/pages and add integration-level tests for the dashboard itself.
05

Telling This Story

The useful split here is that almost every open gap is a productization gap, not an engineering gap. The multi-tenant schema, the entitlement/permission layer, the retry-and-backoff agent design, the audit logging, the migration discipline — that's the part employers actually probe on in interviews, and it's already real. What's left (billing, an installer, SSO, compliance docs) is scoped, well-understood work, not open engineering risk. That's a stronger position than either "impressive demo, unclear if it's real" or "real product, but I can't explain the architecture" — this one has the architecture story and a credible, itemized path to shipping.
